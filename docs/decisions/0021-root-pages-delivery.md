# ADR0021 — Owner-controlled root Pages delivery

28 November 2026. The owner requested and approved https://suduyhien.github.io/. The owner created the free suduyhien organization under sugia279; its public suduyhien.github.io repository was created without transferring the canonical sugia279/hiens-nha source. Implementation is a candidate until the release checkpoint records delivery and hosted Auth verification.

Separate source identity from Pages target identity. Default builds retain sugia279/hiens-nha and its project base; explicit root-target builds use https://suduyhien.github.io and base /. Links to source/issues remain on the canonical repository. Existing content, media references, DB entity IDs, roles, epochs and writers remain unchanged. Public page comments continue sending the existing /hiens-nha/ discussion keys; feed links map those stored keys to the current presentation base. No new entities or content migration is needed.

The destination calls a reusable workflow in the canonical source. It checks out an exact current main commit, requires its main Backend foundation checks to have succeeded, and runs the existing frontend gates against the root build before deploying with the destination's own GITHUB_TOKEN/Pages OIDC. No cross-repository PAT, deploy key, Supabase service key or OAuth secret is needed. Public browser configuration only is stored in destination variables. Manual dispatch and a bounded scheduled source check keep delivery independent of source ownership; unchanged deployed source commits skip rebuilds. The source workflow preserves the Archive guestbook/Pages trigger coupling.

Validate both project and root artifacts, canonical/RSS/sitemap/search/VI–EN/legacy paths, stable discussion contexts and root callback URLs. Keep old hosting operational until the new origin's read-only checks and real owner-consented OAuth succeed. A later old-host redirect must preserve path/query/hash and allow in-flight old Auth callbacks to finish; never copy tokens or sessions between origins. Reauthentication on the new origin is explicit.

Add only exact new CORS origin and VI/EN Auth callbacks, retaining the existing entries during transition. Production Auth/security changes require action-time confirmation in the dashboard. Supabase provider callbacks, owner assignments and guest privileges remain unchanged. Test locally/staging before production; never create production test comments/reactions. Rollback keeps the old deployment and removes only the new publishing/origin entries after review, without restoring stale DB data.
