# ADR0017 — Resource references and post media frames

Accepted 19 November 2026 at the owner's request. Keep one authoritative Auth/publication DB. Add a private resource catalog (provider, endpoint, bucket, credential reference, writable state, capacity) and an asset inventory keyed by resource/path. Secret values are never in the catalog or browser. Current resources resolve to this project's private Storage; external resources remain disabled until an authority-checking broker/adapter is deployed. This is a foundation for multiple stores, not distributed SQL transactions or automatic quota failover.

New revision media references persist resourceId/path/kind and layout/frame. Legacy social.images references resolve to primary-images without moving bytes. Keep layouts shared with the Banner, filter by attachment count, reset invalid choices after removal. MP4/WebM video uploads are bounded to 20 MiB, four mixed attachments per post; images retain WebP conversion and 2 MiB cap. Playback uses controls, no autoplay. A private bucket checks owner upload paths, exact public revisions for guest reads, and denies deletion of historical references. Asset inventory is registered transactionally on save after verifying the local object metadata. Local uploads can only target registered writable local resources. Foreign endpoints are never accepted from post input.

Composer uses a shorter text field and a persistent empty preview area under it. Successful save/publish closes the dialog and refreshes the Home feed through the existing lifecycle event. No window reload or hosted test posts. Existing source/epoch/roles remain unchanged.

Deploy additive migration before frontend. Provision Storage after its local schema starts, like ADR0013. Roll back frontend/Edge together; retain resource catalog, files, revision metadata and policies. DB-only backup still excludes file bytes. External project credentials, cross-project Auth authorization, object-byte backup and dynamic capacity routing are future operator work, not implicitly enabled by this migration.

## iPhone media fix — 21 November 2026

The original allowlist rejected HEIC/HEIF and QuickTime MOV before the upload request, and failures left an empty selection that could still be posted as text. Selections now preview immediately with pending/failed/ready states; pending or failed files block submit until retried or explicitly removed. A native HTML image decoder is used if createImageBitmap cannot decode HEIC/HEIF. It still re-encodes supported decoded images into bounded WebP; browsers unable to decode HEIC show a retained error with JPG guidance. MOV is admitted as private video/quicktime (20 MiB), with path/MIME validation and the existing exact-revision read policies. Video playback depends on browser codec support; original videos are not transcoded. The additive iphone_post_media migration must precede the new Edge allowlist and frontend. No visibility, source or owner changes. File-byte backup remains separate.


## Safari encoding, 50 MiB selection and deletion — 21 November 2026

The previous fix handled native image decoding but still required WebP output. A browser may return PNG for an unsupported requested WebP encoder even though the selected image previews correctly. Try JPEG encoding when WebP is unavailable, name objects by their actual MIME, and admit bounded JPEG on the existing resource-qualified media path without changing legacy WebP paths. Read/decode, input size, conversion and transfer errors must be distinct. Selected photos and videos accept up to 50 MiB per file; photos are resized to 1600 pixels and encoded to at most 2 MiB before upload. The private post-media bucket/resource limit becomes 50 MiB, retaining current owner and exact-published-revision policies and four attachments per post. No unlimited files, new resource or permission changes.

Owner Home cards expose Delete with a confirmation dialog. Cancel sends no request. Confirm uses the existing version-checked soft-delete publication API, refreshes the feed and clears that post from an idle composer. Existing account deletion also asks for confirmation. Deletion immediately withdraws public reads; historical revisions/file bytes remain protected for retention, with no physical Storage deletion. Deploy the additive storage/validator migration and Edge API before the frontend.
