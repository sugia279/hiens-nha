# Post reactions and provider chooser (ADR0016)

Additive migration: `20261120103301_post_reactions.sql`. These are Data API POST RPCs, separate from the existing Edge routes. Use the project's publishable key and optional caller JWT; no service-role client. No source markers or role assignments change.

| RPC | Input | Result / authority |
| --- | --- | --- |
| `post_reactions_read` | `p_ids: uuid[]`, at most 50 | Array of `{post_id, heart, laugh, wow, mine}`; only undeleted published posts; `mine` is caller's `heart/laugh/wow/null`, anonymous always null. Unknown/private IDs omitted. Empty input returns `[]`. |
| `post_reaction_set` | `p_id: uuid`, `p_reaction: heart/laugh/wow/null` | Same summary object. JWT required; actor exclusively from `auth.uid()`. Sets/replaces one row or removes caller's row. Same-value retries cannot toggle/double count. |

All reads and writes consume existing shared admission exactly once. Writes acquire admission before feature/publication locks, matching other write wrappers to avoid lock-order inversion. They reuse `feature_guard('posts')` for source/API epoch/writer gates and successful-mutation quota (30/member/min, 120/owner/min). Table RLS is enabled with all direct browser grants revoked; public wrappers are invoker functions calling scoped private definer functions with empty search paths. Publication SHARE lock serializes writes against delete/unpublish; the `(post_id,actor_id)` primary key enforces uniqueness. Private/draft/deleted posts yield 404 even for owner; no reaction list or other reactor IDs are exposed. Removing a post from public visibility retains rows for a future republish, without exposing counts while private. Reads reject >50 IDs (422); invalid kinds 422, maintenance 503, quota/admission 429. Anonymous writes are denied by function grants (42501).

The post chooser reads the public `GET /auth/v1/settings` endpoint to discover only `github/google/facebook` availability; it sends no session JWT. The provider selected is passed to the existing Auth SDK `signInWithOAuth` with PKCE and the same-origin VI/EN callback. Unavailable providers remain disabled. Provider setup requires the owner to enter OAuth client credentials directly into Supabase, never into the repository/chat. Read-only production settings on 20 November 2026 showed GitHub enabled and Google/Facebook disabled. Relevant official setup: [Google](https://supabase.com/docs/guides/auth/social-login/auth-google), [Facebook](https://supabase.com/docs/guides/auth/social-login/auth-facebook).

Session storage uses the existing project+base key, now a version 2 envelope containing only sanitized Supabase session data. Unexpired v1 records migrate on read; corrupt/expired legacy records are removed. New sessions have no app deadline. Supabase expiry/revocation, cleared storage and explicit device logout can still require login. No provider-token, PKCE, photo-token or role changes. See [Supabase session behavior](https://supabase.com/docs/guides/auth/sessions).

Deployment order: migration to staging, grants/RLS/read checks without hosted test content, production, then frontend. The SQL is now applied to both projects; [PR61](https://github.com/sugia279/hiens-nha/pull/61)/Pages tracks frontend delivery. [Verification](../project/inline-post-interactions-verification-2026-11-20.md) records observed gates separately from pending deployment checks. Configure Google/Facebook apps separately before treating those logins as available. Rollback frontend while retaining additive rows/functions and all uploaded assets; old frontend understands no reaction data and can ignore it. An older v1-only frontend will discard v2 session envelopes and require login once.
